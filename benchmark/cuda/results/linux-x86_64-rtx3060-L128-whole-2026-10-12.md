# L128 host whole-run probe: one RTX 3060, 2026-10-12

The latest verified public-runner measurements give an observed CPU/GPU elapsed-time ratio of **6.33× for optimization** and **5.00× for PhysCal**. The requested **20× target is not met**. The first measured implementation achieved 5.22× and 3.59×; both results are preserved below. These whole-run timings include parsing, parameter/configuration initialization, sampling, numerical work, SR in optimization, and each runner's final output/returned summary. They are distinct from fixed-configuration kernel benchmarks.

## Measured configuration

- Linux x86_64, kernel `6.8.0-146-generic`; Intel Xeon E5-2699 v3 @ 2.30 GHz. `lscpu` confirms AVX2/FMA and **no AVX-512**.
- Julia 1.13.1; one Julia thread and one OpenBLAS ILP64 thread. GPU 1 is a single NVIDIA GeForce RTX 3060, compute capability 8.6, driver 580.178.04. GPU 0 served separate correctness work and contributes no throughput to these results.
- Input: `benchmark/cuda/inputs/hubbard_chain_L128/namelist.def`, 128 sites, 128 electrons in total, real/Sz-conserved pairing, eight spin-projection sectors, 772 parameters.
- Optimization: **20 SR steps**, **300 configurations per step**, `NSRCG=0`, final CPU optimization window `NSROptItrSmp=1`.
- PhysCal: one sampling run/batch of 300 configurations, with the same initialized fixed-parameter checkpoint on CPU and GPU.
- **Warmup=1 and interval=1 sweeps**, with 128 attempted proposals per sweep. This is a short-run performance probe; it does **not** use the original input's warmup of 10 sweeps, nor establish equilibration or effective sample sizes.
- One cold first execution followed by three warm full-run repetitions. Warm repetitions still repeat parsing, initialization and all runtime work; only first-use compilation is warmed.
- GPU modes at measurement: resident GPU initialization, cached inverse/rank-update sampling, uniform-empty hopping destinations, exact incremental Gutzwiller/Jastrow counts, sampling-cache reuse for observables, native cuSOLVER SR and resident parameter gauge. Float64 numerical calculations were retained.

## Sampling and output scope

The CPU runner uses one sequential SFMT chain, stores 300 thinned configurations, and reuses its burn state. The GPU runner uses 300 independent XORWOW chains, performs an initial warmup for every chain, and takes one configuration from each chain per batch. Both select empty hopping destinations for this nonlocal-spin, half-filled input. They have different RNG streams/draw semantics and initial configurations.

| Configured attempted-proposal budget | CPU | GPU |
|---|---:|---:|
| Optimization, including warmup | 770,560 | 806,400 |
| PhysCal, including warmup | 38,528 | 76,800 |

CPU's first sampling call uses `(warmup + samples) × interval × Nsite` attempts; later calls use `(samples + 1) × interval × Nsite`. GPU uses `walkers × (warmup × interval × Nsite + batches × interval × Nsite)`. For this pure-hopping input with no local-spin sites and available empty destinations, every configured proposal has a legal candidate; that is a model/proposal deduction, not a measured counter. These counts are not effective sample sizes. Full accepted/valid counters are not exposed by the public runners. GPU's final interval accepted 13,994 moves in optimization and 14,325 in PhysCal in every repetition; these are only final-interval counts.

The CPU public runners write C-format per-step/final parameter, energy and Green files. GPU runners return numerical arrays and resident state, with their final summaries/transfers included in GPU timing; equivalent C-format files are not written. CPU PhysCal energy-file readback and the benchmark's acceptance/finite-result checks happen after the timed runner call. The displayed ratios therefore measure the documented runner lifecycles, not equivalent RNG trajectories or proven effective-sample throughput.

## Warmed inner-loop transfer audit

A separate GPU 0 CUPTI audit excluded setup and compilation, warmed one complete production optimization iteration, and profiled two subsequent 300-walker iterations through sampling, observables, derivatives, SR, parameter gauge, Slater refresh and sampling-cache refresh. Final solver-status, energy-history and parameter readbacks occurred after profiling. This is a transfer audit, not an additional GPU throughput result.

The profiled application boundary contained **12 host-to-device copies**, **zero device-to-host copies**, and **two device-to-device copies**. Consequently, this measured pre-follow-up source had residual H2D traffic. H2D copy activity totaled 7.63 microseconds on the device; the corresponding host API activity totaled 85.35 microseconds across two iterations. The profiled final parameters were finite. [The raw CUPTI log](L128-whole-inner-loop-CUPTI.txt) preserves the copy names and counts; the developer script is `/tmp/profile-julia-whole-inner-loop.jl`. Scalar uploads from generic numerical-library wrappers are suspected, but this audit alone does not attribute each transfer to its caller.

### Resident SR moments follow-up

Phase-level CUPTI probes located all six uploads per iteration: two scalar arguments for each of the OO and HO products, and two for CUDA's GEAM-based matrix subtraction. Mean reductions and the outer product uploaded no scalars; native cuSOLVER uploaded none. The production follow-up reuses the SR workspace's resident alpha/beta pointers for OO and HO and performs elementwise covariance subtraction, preserving the existing outer-product calculation and division order. The generic implementation remains an independent GPU reference.

After that change, the same warmed two-iteration host-side audit recorded **zero H2D**, **zero D2H**, and **two D2D** application copies, with finite final parameters and unchanged reported energy history. [The follow-up raw CUPTI log](L128-whole-inner-loop-CUPTI-resident-moments.txt) preserves this result. Ten independent CPU/generic-GPU moment comparisons, five native-solver checks and sixteen complete L128 runner checks passed without relaxing tolerances. These are host-side correctness/transfer checks; the earlier elapsed-time tables measure the preceding source and are not reattributed to this change or to the Dev Container.
