# CUDA backend: Linux RTX 3060 measurements (2026-10-12)

## Scope and environment

These are warmed, fixed-configuration kernel/workload measurements, not complete
optimization/PhysCal speedups. GPU0 ran correctness/debugging; GPU1 ran these
benchmarks, with no second compute job on GPU1. CPU comparisons evaluate identical
configurations, Hamiltonian/Green quantities and analytic parameter derivatives.
Setup, parameter initialization, compilation and model uploads are excluded.
Five synchronized repetitions report min/median/max; tables use wall-time medians.
CUDA-event medians are also preserved in the accompanying text results.

Linux x86_64, Ubuntu kernel6.8.0-146-generic; Intel Xeon E5-2699v3@2.30GHz;
NVIDIA GeForce RTX3060 (12GiB, sm86); Julia1.13.1; CUDA.jl/CUDACore6.4.2;
GPUArrays11.5.16; GPUCompiler2.13.4; LLVM20.1.8; CUDA runtime13.4.0 and compiler
13.4.92 (artifacts); NVIDIA driver580.178.04; forward-compatible driver artifact
for CUDA13.3; cuBLAS13.8.0; cuSOLVER12.3.4; cuRAND10.4.4; CUPTI2026.3.1.
Native CPU compiler: GCC/GFortran 13.3.0 (Ubuntu 24.04 packages).
CPU BLAS: OpenBLAS ILP64 (`libopenblas64_.so`), one thread. Production proposal
words: cuRAND XORWOW, seed79. Walker kernels use32 threads/block and walker-first
workspaces; Slater/cofactor contractions use double-precision cuBLAS.

Reference CPU source is upstream Julia-mVMC62416e30a04e33a6d3641351fa8487dd640473cb,

Small batches do not guarantee a speedup: the L16/256 case is slower on this GPU.
Larger batches amortize launches and improve occupancy. RTX3060 has limited FP64
throughput; these results do not generalize to other GPUs/BLAS providers or imply
that one GPU Markov chain beats a CPU chain.

## Residency verification

The warmed CUPTI region includes CUDA-generated proposal words,20 attempted
proposals per walker, energy/Green calculations, analytic cofactor sensitivities
and their GEMM contraction. All three runs recorded **zero memory-copy records**
in that application region. The profiler's own dummy Int64 upload before its
first synchronization is excluded using its documented display boundaries.
Matrix GEMM alpha/beta scalars are resident; generic CUDA `mul!` would upload
scalar references on every call.

Optimization boundaries still read solver status, maximum variance, energy and
O(NPara) parameters for CPU C-compatible gauge shifts/rescaling. PhysCal copies
its summary once. Callbacks may explicitly copy additional data. These transfers
are not hidden by the inner-region measurement.

## Correctness gates

GPU0:2022 assertions passed, including real/complex batched Pfaffians, sparse
closed-form skew matrices, projected wavefunctions, CPU energies/Greens/analytic
SR derivatives/updates, every proposal and decision on20-step shared UInt32 tapes,
future-word and configuration repeatability on20-step production runs, input
rejection, all5259 ordinary one/two-body operator quantities on8 configurations,
and exact cofactor derivatives for a synthetic nodal QP sector.

Hubbard/Heisenberg SR comparisons measured derivative differences below2.7e-14,
observable differences below1.2e-13, stabilized-system condition numbers2.30e3
and5.33e6, update differences2.32e-15 and2.02e-11, and solver residuals below1.2e-16.
Update comparisons use explicit1e-9 absolute/relative tolerance plus a residual
gate. Synthetic sparse/nodal mathematical checks are distinguished from CPU
full-normal-factorization parity; no floating-point bitwise comparisons are used.

CPU-only gates on Julia1.13.1 passed: MVMCOptimizers unit suite (45349 assertions
in its main unit group), full integration runner (including C-reference Lanczos
and PairHop), PhysCal C references (31), and C ctest-equivalent gates (66).
Native macOS GPU execution is unsupported; CPU portability is covered by upstream
Linux/macOS CI. This report records local Linux results only.
